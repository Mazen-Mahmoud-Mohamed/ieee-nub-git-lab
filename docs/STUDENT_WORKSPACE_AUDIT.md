## Root causes and reproduction

The actual hosted Assignment 01 was fetched from `spldzxeqxwicnffnkizm`, assessment `b6f4b6d0-5fe2-4e4d-b9a5-000000000001`, published version 1. Its public document is preserved in `tests/fixtures/published-assignment-01-v1.json`. It has 12 scored written/scenario questions worth 25, two required zero-point reflections and one optional zero-point bonus reflection. It contains no MCQ; objective controls were therefore audited separately with reusable assessment fixtures rather than inventing questions for Assignment 01.

The filesystem always returned inode/time zero. Git reused cached index information for same-size writes and incorrectly showed modified tracked files as clean. A controlled reproduction confirms explicit `git add` still reads the changed text and can produce the correct second commit; a successful command message was not evidence of correct live status. The new regression asserts actual working/index states, second-commit contents, parent OID, history and restored behavior. Monotonic whole-second virtual stat ticks fix the cache alias without changing snapshot format or server exam clocks. Trusted grading still independently compares working files with committed trees.

Additional missing points came from version 1 compatibility predicates: setup secretly required a first commit; file preparation required committed contents; separate introductions had an incidental strict order; the goals update required exact numbered-list counts and placement after the notes commit. The UI showed repeated section instructions, a permanently displayed history graph, multiple progress summaries and remote-looking navigation instead of one task. The Questions action was buried behind practical gating, required-answer counts excluded the two mandatory reflections, and short answers used the same large textarea as long answers. The corrected UI exposes one Questions step, valid controls and required-response states. A separate submission defect retained definitely rejected payloads, causing corrected answers to be replaced by old outbox evidence on retry; rejected validation/conflict payloads are now cleared while ambiguous network retries keep idempotency.

## Version and scoring policy

Version 1 is immutable. Existing attempts and released grades keep their original version and compatibility revision. The filesystem, synchronization, Questions rendering and retry fixes apply generally. A corrected Assignment 01 version uses explicit compatibility rule revision 2, concise task instructions, no undocumented introduction order, normalized personal labels/whitespace and goal lists, and historical parent/tree evidence for the tracked update. Staging is visible preparation; official update credit needs a real later commit on main and does not require a committed file to remain staged. Questions are accessible throughout in the new version, while required tasks/answers remain enforced at manual submission. Existing gated versions retain their published gate.

No database schema/RLS, instructor dashboard redesign or new arbitrary execution rule is introduced. Version publication uses the existing authorized `save_assessment` RPC after both client and trusted verifier support the revision. Publication checks the version 1 document hash and all existing attempt/version associations before and after; existing private rubrics are copied privately to the new version.

## Remaining limits

New attempts use version 2. Existing version 1 attempts keep their original stricter scoring/gating contract and history; they benefit from the filesystem, workspace, Questions and retry fixes without being silently migrated. An instructor-approved retake uses the current version when the existing attempt lifecycle permits it. Written answers always need authorized manual marks. Requirements such as a clean current main branch are state-dependent and can legitimately regress after edits or branch changes; historical committed-update evidence persists. Local points are provisional until trusted server verification. Fresh hosted authentication depends on network availability; staged tests encountered and recovered from intermittent network startup delays. The deployment remains staging and its real database counts include retained synthetic acceptance records.
